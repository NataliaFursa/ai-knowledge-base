# Agent Skills в Claude Code и OpenAI Codex

Скилл - это набор повторно используемых инструкций и материалов для определённого вида задач. Он сохраняет
процедуру, которую иначе пришлось бы объяснять агенту в каждой сессии. Например, создание состояния в state
machine включает класс, методы жизненного цикла, регистрацию и переход. Документирование модуля требует изучить
публичный API, отделить собственные сущности от внешних зависимостей и проверить текст по коду. У обеих задач есть
устойчивая последовательность, поэтому она подходит для скилла.

Скилл может задавать правила, расположение файлов, принятые соглашения, условия остановки, пример результата,
справочники, шаблоны и скрипты. Claude Code и OpenAI Codex используют общую модель
[Agent Skills](https://agentskills.io/specification): основой служит директория с `SKILL.md`. Пути хранения,
ручной запуск и дополнительные настройки различаются.

## Когда выбирать скилл

Механизм зависит от того, насколько широко действует правило. «Перед изменениями согласуй план» относится ко
всей работе в репозитории и должно находиться в постоянных инструкциях. Процедура добавления состояния или
написания документации нужна лишь в одном классе задач и может стать скиллом.

| Механизм | Claude Code | OpenAI Codex | Назначение |
| --- | --- | --- | --- |
| Постоянные инструкции | `CLAUDE.md` | `AGENTS.md` | Правила для большинства задач проекта |
| Скилл | Директория с `SKILL.md` | Директория с `SKILL.md` | Повторяемая процедура определённого вида |
| Сабагент или внешнее подключение | Сабагенты, MCP, плагины | Сабагенты, MCP, плагины | Отдельное исследование или доступ к внешней системе |

Один скилл лучше связывать с одной распознаваемой целью. Если две процедуры имеют разные условия запуска,
входные данные или критерии успеха, их разделяют. Это не запрещает агенту использовать несколько скиллов в
одной задаче: общие правила написания кода и процедура создания конкретного окна могут дополнять друг друга.
Противоречия между ними нужно разрешить до использования.

## От обнаружения до выполнения

При запуске агент получает список доступных скиллов. На этом этапе в контекст попадают метаданные, прежде
всего `name` и `description`. Codex также показывает путь к скиллу. Полная инструкция пока не загружается.
Поэтому пользователь может описать задачу обычными словами, а агент выбирает подходящий скилл по его
`description`. Можно вызвать его и явно.

| Способ | Claude Code | OpenAI Codex |
| --- | --- | --- |
| Автоматический | Запрос соответствует `description` | Запрос соответствует `description` |
| Ручной | `/writing-module-docs` | `$writing-module-docs`, в CLI и IDE также есть `/skills` |

После выбора агент читает `SKILL.md`. Справочные файлы он открывает, а скрипты запускает по указанному условию.
Такой порядок называется progressive disclosure: подробности хранятся рядом с процедурой, но не занимают
контекст каждой задачи. Прочитанный справочник добавляет в контекст свой текст, а для скрипта обычно важен
результат выполнения. Поэтому скрипту нужен понятный способ запуска и информативный вывод.

В `SKILL.md` следует прямо указать, какой файл и при каких обстоятельствах читать, а какой скрипт и когда
запускать. Нельзя рассчитывать, что агент сам догадается о назначении соседних материалов. Размеры начального
списка, полной инструкции и дополнительных файлов различаются. Они разобраны в [статье о лимитах](limits.md).

## Размещение скиллов

Минимальный скилл состоит из директории и `SKILL.md`:

```plain
<skills-root>/
  writing-module-docs/
    SKILL.md
```

| Область | Claude Code | OpenAI Codex |
| --- | --- | --- |
| Весь проект | `.claude/skills/<name>/SKILL.md` | `.agents/skills/<name>/SKILL.md` |
| Пользователь | `~/.claude/skills/<name>/SKILL.md` | `~/.agents/skills/<name>/SKILL.md` |
| Область репозитория | `<подпапка>/.claude/skills/<name>/SKILL.md` | `<подпапка>/.agents/skills/<name>/SKILL.md` |

Проектный скилл находится в репозитории и доступен команде. Личный действует на текущей машине. Процедуру для
всего проекта кладут в корень, а процедуру одного модуля можно разместить рядом с ним. Это размещение важно:
агенты ищут скиллы относительно рабочей директории, а не сканируют весь репозиторий при каждом запросе.

## Как агенты находят скиллы в репозитории

Текущая рабочая директория (`CWD`) - папка, из которой запущен агент. Оба инструмента ищут проектные скиллы в
ней и выше, до корня репозитория. Сначала агент определяет корень по маркеру, затем собирает скиллы на участке
между корнем и директорией запуска. По умолчанию маркером служит `.git`. Для Codex его можно изменить через
`project_root_markers` в `config.toml`, например `[".git", ".hg", ".sl"]`. Пустой список делает корнем `CWD`.
Claude Code ориентируется на корень Git-репозитория, а в связанном worktree - на корень worktree.

Скилл выше определённого корня не загружается. Если домашняя директория случайно является Git-репозиторием,
результат может оказаться неожиданным: обе системы сочтут её корнем и включат скиллы на пути до директории
запуска. Поведение вложенных скиллов лучше видно на примере:

```plain
repo/
  .claude/skills/root-skill/
  .agents/skills/root-skill/
  apps/
    .claude/skills/apps-skill/
    .agents/skills/apps-skill/
    shop/
      .claude/skills/shop-skill/
      .agents/skills/shop-skill/
      checkout/
        .claude/skills/checkout-skill/
        .agents/skills/checkout-skill/
        PaymentService.cs
```

Если агент запущен из `repo/apps/shop`, в начале доступны `shop-skill`, `apps-skill` и `root-skill` своего
вендора. `checkout-skill` находится ниже `CWD`, поэтому в начальный список не входит. Дальше поведение
различается.

### Claude Code

Claude Code проверяет `.claude/skills` от `repo/apps/shop` до `repo`. По
[документации Anthropic](https://code.claude.com/docs/en/skills), скилл вложенной директории обнаруживается,
когда агент начинает читать или менять файлы в ней. После обнаружения он остаётся доступным до конца сессии.
До этого `checkout-skill` не отображается в меню `/` и не вызывается по имени. Для раннего подключения можно
использовать `/add-dir` с путём `checkout` или начать сессию внутри подпапки.

### OpenAI Codex

Codex проверяет `.agents/skills` от рабочей директории до корня проекта. В
[документации OpenAI](https://learn.chatgpt.com/docs/build-skills) не заявлено автоматическое обнаружение
скилла в дочерней папке после чтения её файлов. Поэтому `checkout-skill` нельзя считать доступным при запуске
из `repo/apps/shop`. Гарантированный путь - запустить новую сессию из `repo/apps/shop/checkout` или ниже.
Тогда к `checkout-skill` добавятся скиллы трёх родительских уровней.

### Запуск вне репозитория

Если маркер корня не найден, Codex ищет проектные скиллы только в `.agents/skills` текущей директории.
Личные, администраторские и встроенные скиллы остаются доступны. Для Claude Code в исходной статье описан
поиск `.claude/skills` по родительским директориям. Это результат проверки на Claude Code 2.1.280, а не
документированная гарантия Anthropic. Поведение может измениться. Поэтому проектные скиллы надёжнее использовать
при запуске внутри репозитория.

Главное различие состоит в обнаружении вложенной папки: Claude Code может подключить её скилл по мере работы
с файлами, а для Codex следует выбрать эту папку рабочей директорией. Оба инструмента видят скиллы от `CWD`
вверх до корня проекта.

## Из чего состоит скилл

Обязателен только `SKILL.md`. Справочники, скрипты и шаблоны добавляют при необходимости:

```plain
writing-module-docs/
  SKILL.md
  references/
  scripts/
  assets/
```

Файл `SKILL.md` состоит из YAML-frontmatter и основной инструкции. Для переносимого скилла в frontmatter
достаточно `name` и `description`. Поле `name` должно совпадать с именем каталога. В общее ядро не стоит
добавлять поле одного вендора, если процедура работает без него.

```markdown
---
name: writing-module-docs
description: Writes and updates a module README from its public API and .asmdef.
  Use when asked to document a module or refresh its README after code changes.
  Do not use for project-wide documentation.
---

# Документация модуля

## Входные данные

Прочитай публичный код модуля и его `.asmdef`.

## Порядок работы

1. Составь список публичных типов.
2. Подготовь структуру README и дождись подтверждения.
3. После подтверждения напиши документ.
4. Сверь каждое утверждение с кодом.

## Условие остановки

Если модуль не определён однозначно, остановись и запроси путь.
```

В примере `description` написано по-английски согласно правилам этого репозитория. Это не требование формата:
для русскоязычных процедур описание и инструкция могут быть на русском. Технические ограничения к `name`
остаются прежними: строчные латинские буквы, цифры и дефисы.

## Как написать `description`

Агент видит описание до чтения основной инструкции. Его формулируют в третьем лице: сначала результат,
затем характерные условия запуска словами, которые может использовать пользователь. Если рядом есть похожая
процедура, следует указать исключение. «Помогает с документацией» слишком широко. «Создаёт и обновляет
README модуля по публичному API, но не пишет документацию всего проекта» задаёт распознаваемую границу.

Слишком узкое описание тоже мешает: оно не распознаёт иной запрос с той же целью. Основное действие и
условия применения располагают в начале, поскольку длинные описания могут сокращаться в начальном списке.
Шаги, формат результата и ограничения должны оставаться в основной части `SKILL.md`. Ограничения на длину и
бюджет списка приведены в [статье о лимитах](limits.md).

## Как написать основную инструкцию

До подробного текста нужно определить границы процедуры: какую задачу она решает, что в неё не входит,
какие входные данные обязательны, какой артефакт должен получиться и при каких условиях работа
останавливается. Затем указывают порядок действий, запреты, дополнительные материалы и пример результата.
Не каждой простой процедуре нужны отдельные заголовки для всех этих частей, но каждая существенная граница
должна быть понятна читателю и агенту.

Инструкция должна описывать наблюдаемые действия и результат, а не внутренние рассуждения модели.
«Проверь конфигурацию» оставляет неясными файл и проверку. «Прочитай значение `version` из `package.json`»
устраняет эту неопределённость. Запрет тоже должен указывать безопасное продолжение: «Возьми версию из
`package.json`. Если поля нет, остановись и запроси значение» полезнее, чем «Не придумывай версию».

Когда порядок влияет на результат, шаги нумеруют и формулируют как действия: прочитать публичный API,
составить структуру, показать её пользователю, после подтверждения написать документ. Причину устойчивого
правила добавляют там, где она помогает применить его в новом случае. Например, план сохраняют в файле,
чтобы договорённость пережила следующую сессию. Порядок полей или название файла могут быть просто
соглашением и не нуждаются в придуманном объяснении.

Сбор контекста ограничивают достаточным набором: «Прочитай публичные типы и `.asmdef`. Не открывай
внутренние типы, если на них не ссылается публичный API». Условия остановки называют отдельно. К ним
относятся отсутствие обязательного входа, несколько существенно разных мест для нового файла,
неоднозначное требование и противоречие между инструкцией и кодом. В каждом случае нужно сказать,
что делать дальше: запросить уточнение, показать варианты или остановиться.

В скилле не стоит повторять общеизвестное описание формата или инструмента, если оно не помогает
выполнить процедуру. Если форма результата важна, нужен короткий явно помеченный пример. Иначе агент
может взять случайный образец из проекта или принять пример за обязательную часть инструкции.

### Markdown и XML

Markdown удобно разделяет разделы, шаги и таблицы. XML полезен для точных границ вложенных данных:
входа, примера, документа и его источника. Атрибуты тега могут хранить номер или источник документа.
Это разметка внутри текста инструкции, а не особый механизм
YAML-frontmatter или функция только одного вендора. Оборачивать каждый абзац в XML не нужно.

```markdown
# Проверка документации

## Инструкция

Сверь утверждения документа с публичным API модуля.

## Примеры

<examples>
  <example>
    <input>Обновить README модуля Payments после изменения API.</input>
    <output>README описывает актуальные публичные типы и методы.</output>
  </example>
</examples>
```

Названия тегов должны последовательно отражать содержимое. Вложенность нужна при естественной иерархии,
например `<documents>` -> `<document>` -> `<source>` и `<content>`. XML особенно помогает, когда рядом
находятся сама инструкция и цитируемые данные. Рекомендации по структурированию запросов см. у
[Anthropic](https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/claude-prompting-best-practices)
и [OpenAI](https://developers.openai.com/api/docs/guides/prompt-engineering).

## Уровень свободы инструкции

Подробность зависит от риска отклонения. Для архитектурного анализа может быть несколько правильных решений.
для публикации или миграции последовательность должна воспроизводиться точно.

| Уровень | Форма | Когда применять | Пример |
| --- | --- | --- | --- |
| Высокая свобода | Критерии и ограничения | Выбор зависит от контекста | Ревью кода, анализ архитектуры |
| Средняя свобода | Шаблон, псевдокод, параметризованный скрипт | Форма предпочтительна, но допустимы варианты | Документ по согласованной структуре |
| Низкая свобода | Точная команда или строгая последовательность | Ошибка опасна или результат должен повторяться | Миграция, сборка, публикация |

Избыточная детализация делает скилл негибким. Новые правила лучше добавлять по наблюдаемым ошибкам, а не
по всем воображаемым сценариям. Низкую свободу используют там, где отклонение действительно может
привести к ошибке или невоспроизводимому результату.

## Дополнительные файлы

`SKILL.md` остаётся картой процедуры. В `references/` лежат правила, схемы и большие примеры. В `assets/`
размещают шаблоны и файлы для копирования или преобразования. В `scripts/` - детерминированные проверки
и преобразования. Для каждого материала в основной инструкции указывают ссылку и условие использования.

```plain
Прочитай `references/doc-rules.md` перед подготовкой структуры документа.
Запусти `scripts/check-links.py` после сохранения README.
```

Цепочка, в которой `SKILL.md` ведёт к одному файлу, а он только перенаправляет к следующему, затрудняет
загрузку нужного правила. Для длинного справочника полезно оглавление. Скрипт оправдан, когда результат
должен быть воспроизводимым. Если короткая инструкция со штатным инструментом работает устойчиво,
отдельный скрипт не нужен.

## Вендорские расширения

Общая спецификация покрывает основную процедуру, а вендоры добавляют свои настройки. Claude Code
использует дополнительные поля YAML-frontmatter для подсказки аргументов, ручного и автоматического
вызова, разрешённых инструментов, выполнения в сабагенте и динамической подстановки контекста.
Codex может хранить интерфейсные настройки, зависимости и политику автоматического запуска в
`agents/openai.yaml` рядом со скиллом. Например, в Codex можно запретить автоматический запуск,
оставив ручной вызов через `$имя-скилла`.

Если расширение требуется, его обозначают как настройку конкретного клиента и проверяют там отдельно.
Добавлять вендорское поле в переносимый пример без пояснения не следует. Возможности описаны в
[документации Claude Code](https://code.claude.com/docs/en/skills) и
[руководстве OpenAI](https://learn.chatgpt.com/docs/build-skills).

## Одна процедура для двух вендоров

При поддержке Claude Code и Codex полную процедуру можно хранить один раз, а в каталогах вендоров
оставить небольшие обёртки с метаданными обнаружения и указанием прочитать общий файл:

```plain
repo/
  agent-skills/
    writing-module-docs/
      instructions.md
      references/
      scripts/
  .claude/skills/
    writing-module-docs/
      SKILL.md
  .agents/skills/
    writing-module-docs/
      SKILL.md
```

Обе обёртки могут содержать один и тот же переносимый текст:

```markdown
---
name: writing-module-docs
description: Writes and updates module documentation from its public API.
  Use for a module README or API refresh after code changes.
---

1. Определи корень текущего Git-репозитория.
2. Прочитай `agent-skills/writing-module-docs/instructions.md` от его корня.
3. Выполни описанную там процедуру.
4. Если файл отсутствует, остановись и назови путь, который не удалось найти.
```

Общие изменения вносят в `instructions.md`. Обёртки содержат только метаданные и необходимые вендорские
настройки. Это избавляет от двух расходящихся копий процедуры. При этом путь к общей инструкции должен
быть доступен из среды запуска. Сама обёртка не загружает её автоматически без явного указания.

### Каталог процедур без нативных скиллов

Можно завести собственный каталог с названиями процедур, описаниями и ссылками на Markdown-инструкции,
а в `CLAUDE.md` и `AGENTS.md` попросить агента проверять каталог перед задачей. Хуки также могут
подключать нужные файлы в подходящий момент. Это сохраняет инструкции в одном месте, но не даёт
нативного автоматического выбора и встроенного ручного вызова. Обёртки нужны, когда эти возможности
или вендорские расширения важны.

### Язык инструкции

Английский часто используют для скиллов, но формат не требует его. Русский подходит для процедуры,
которая работает с русскоязычными запросами или выпускает русскоязычный результат. Для этого
репозитория принято писать `description` на английском, даже если основная инструкция русская.
Язык описания следует проверять на реальных формулировках пользователей. Поле `name` остаётся
техническим идентификатором и использует только допустимые латинские символы, цифры и дефисы.

## Как проверять скилл

Работу над скиллом полезно начинать с наблюдаемого пробела. Агенту дают реальную задачу без него,
фиксируют ошибку, готовят сценарии с ожидаемым поведением и пишут минимальную инструкцию. Затем
сценарии повторяют в новой сессии со скиллом и без него. Новая сессия важна: контекст обсуждения
может скрыть недостатки самой инструкции.

Проверку выбора и проверку результата разделяют:

| Сценарий | Ожидаемое поведение |
| --- | --- |
| Прямой запрос | Скилл запускается для явно названной задачи |
| Косвенный запрос | Распознаётся та же цель в другой формулировке |
| Неполные данные | Агент задаёт нужный вопрос |
| Похожая неподходящая задача | Скилл не запускается |
| Граничный случай | Агент не выдумывает сведения и не выполняет неподдерживаемое действие |

Для каждого вендора отдельно проверяют ручной запуск (`/имя-скилла` и `$имя-скилла`) и
автоматический выбор по `description`. Если скилл не выбирается или выбирается для лишней задачи,
меняют описание и границы применения. Если он выбран верно, но нарушает порядок, уточняют основную
инструкцию. Если открывает не те файлы, уточняют пути и условия загрузки. Если справочник читается
всегда, обязательную часть можно перенести в `SKILL.md`. При различии поведения у вендоров
проверяют размещение, способ запуска и настройки обёртки.

Скилл тестируют на всех моделях и средах, для которых он предназначен. Подробность, необходимая одной
модели, может излишне ограничить другую. Инструкцию расширяют по результатам проверок, а не по
предположениям о возможных ошибках.
